JailBee

Who JailBee is for.

Four projects come up whenever this one does. They are all good, and they sort into two families answering two different questions: how do I get the right toolchain, per branch? and how do I stop the agent from wrecking my laptop? JailBee answers both at once, which is exactly why it is heavier than either.

The short answer.

Pick Dev Containers if a shared toolchain is what you need, or if anyone on the team is on macOS or Windows. It is the standard, and JailBee has nothing to add.

Pick Docker Sandboxes if you need a hypervisor between the agent and your laptop. Its microVM is a genuinely stronger boundary than JailBee's.

Pick JailBee when the runtime is the hard part: a stack that boots, listens, renders and occasionally wants /dev/kvm — several of them at once, with an agent working behind the fence.

Isolation by boundary, not by allowlist.

Most sandboxes work by enumeration. You declare which paths, which hosts, which syscalls, which tools — and everything the workload does has to fit through that list. It is precise, and it works beautifully when you know in advance what the workload will do.

Agentic development is the case where you don't. The agent decides it needs docker compose up. Then an emulator. Then a headless browser, then a real one. Then a package manager you have never installed. With an allowlist, every one of those is a policy change, and each one widens the policy for everything else — so the isolation degrades exactly as the work gets interesting.

JailBee moves the boundary instead of enumerating through it. The container is the boundary; what happens inside is your business. Adding a tool costs nothing, because nothing was enumerated in the first place.

The four, briefly.

  • Dev Containers The default answer in this space and the one most teams should try first. It is a toolchain boundary, not a containment one, and its defaults point away from containment: your folder is bind-mounted read-write, so an agent inside edits your real tree; credential helpers and your SSH agent are forwarded by design; and the two supported ways to get Docker inside are a privileged docker-in-docker feature or bind-mounting the host's Docker socket, which is host root by another name. devcontainer.json declares the tools a repo needs; .jailbee/config.yaml declares the machine it needs.
  • BranchBox The closest thing to JailBee's shape: a worktree plus a Compose project plus a generated devcontainer, per feature. Much lighter to adopt, and it runs on macOS. It inherits the devcontainer posture and goes further in the same direction — tool credentials are mounted read-write into every feature by design. It solves collisions between your own parallel workstreams; it is not built to contain something you don't trust.
  • nono A fence around the agent process — no container, no VM. Its per-tool policies are finer-grained than anything JailBee does: the agent may call gh, but gh gets its own filesystem grants and a proxied token. It is the allowlist model, and it cannot give you a second Postgres or a second port 3000, because it is not an environment. Its own docs recommend running it inside a container when you need guest/host isolation — running nono inside a JailBee container is a sensible combination, not a contradiction.
  • Docker Sandboxes The one tool here with a stronger boundary than JailBee's, and it should be said plainly: each sandbox is a microVM with its own kernel, and its egress proxy injects API keys into requests so credentials never enter the VM — strictly better than JailBee, which bind-mounts your gpg-agent and SSH sockets and trusts the container boundary to hold. What it is not is an environment for a branch. sbx puts a stronger wall around one agent run; JailBee gives you a whole machine per branch with a weaker — though still kernel-enforced — wall around it.

When not to use JailBee.

  • You're not on Linux. The macOS path runs JailBee inside a Linux VM and is experimental.
  • You need a hypervisor boundary. A system container shares the host kernel, so a kernel bug is an escape path. It is the right boundary for code you are supervising loosely, not a multi-tenant boundary against a determined attacker.
  • Your stack is one process and one database. git worktree plus docker compose -p is free and already installed.
  • You want it working in ten minutes. Host setup — Incus, UID delegation, firewall, kernel keyring limits — is an afternoon, once. The golden image is another 10–15 minutes, once per repo stack. After that, containers are copy-on-write clones and creation is fast.
  • You want your editor wired up for you. jailbee ide knows the JetBrains launchers, and there is no Dev Containers integration. VS Code is not ruled out — the passthrough is generic, so installing it into the golden image and starting it from a shell works — but nothing ships to do it for you.
  • Your secrets must never sit in the environment. Key material stays on the host — GnuPG and SSH reach the container as sockets — but an API token a repo mounts is a file in the container like any other. A credential proxy (nono, sbx) is the stronger design for those.
